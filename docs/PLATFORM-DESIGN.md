# Platform Design - UI & Backend API

Working reference for anyone (human or agent) joining `agentic-ai-platform-demo` in
progress. Scope: the console app (`console/`) - UI shell, API surface, data
stores, and the change history that produced them. Generated by scanning the
repo at HEAD `3885d25` (branch `feat/three-layer-persona`); every claim below
traces to a file/line in this tree, not to memory of the spec.

> **Writing a script, test, or agent against this API? Read
> [`API-GOTCHAS.md`](./API-GOTCHAS.md) first.** This document says what the code
> does; that one lists the endpoint names, response shapes, id namespaces, and
> irreversible-side-effect traps that have actually cost review time (wrong
> guesses produce assertion failures that look like product bugs). It also carries
> the assertion patterns the review side uses to sign a batch off.

## 1. UI Architecture

### 1.1 Shell navigation (`SHELL_NAV`, index.html ~504)

Five persona shells, each an array of `[id, label, icon, view, tabKey, tabValue]`.
`SHELL()` picks the active shell from the signed-in session; `SHELL_VIEWS`
(index.html ~570) is the display-gating list of routable views per shell - the
server re-checks every capability independently, so this is UX gating only.

| Shell | Nav items (id → view) |
|---|---|
| `builder` | fleet→workspace(fleet tab), build→compose, memorykb→workspace(memorykb tab), cost→workspace(cost tab), obs→observability, registry→registry |
| `lead` | dashboard→domainconsole(dashboard tab), projects→domainconsole(projects tab), users→domainconsole(users tab), governance→governance |
| `admin` | home→platformconsole, domains→domains, blueprints→blueprints, memory→memory, ai-gateway→ai-gateway, registry→registry (org), governance→governance, cost→cost, observability→observability |
| `user` | overview→overview, fleet→fleet |
| `buildworkspace` (not a shell - a shared nav list) | bwfleet→workspace(fleet), bwbuild→compose, bwmemorykb→workspace(memorykb), bwcost→workspace(cost), bwobs→observability, bwregistry→registry |

Notes:
- `builder` nav IS the project workspace tab bar - no separate Governance tab
  (request-access is an inline action inside Memory & KB / registry detail,
  never a nav destination).
- `admin` has no `buildworkspace`-style build entries of its own listed above
  because those live in the second section (below) - the platform is treated
  as a domain like any other (spec v2.5 §0).

### 1.2 Dual-section sidebar (spec v2.5 §2, TLP-B9)

`HAS_BUILD_SECTION = { admin:true, lead:true, builder:false, user:false }`
(index.html ~597). Admin and lead each render **two** sections:

1. A governance section - their own `SHELL_NAV[shell]` list, labelled via
   `GOV_SECTION_LABEL = { admin:'PLATFORM', lead:'DOMAIN' }`.
2. A persistent **BUILD WORKSPACE** section - `SHELL_NAV.buildworkspace`,
   structurally isomorphic to the `builder` nav (same six-item shape; a smoke
   assertion checks this equality, spec §6 "nav isomorphism").

Builder and user get a single section (their own list only). This models the
platform itself as a domain: every domain - platform included - gets a
governance surface plus its own build workspace (spec v2.5 §0).

### 1.3 Create Agent journey - three doors (`DOORS`, index.html ~4485)

Current order (TLP-B10, corrected from an earlier B8 misread - see §4):

| Order | id | Title | Preset | Landing / behavior |
|---|---|---|---|---|
| 1 | `blueprint` | Start from Blueprint | FULL | Pick an approved Blueprint, compose harness, test, export |
| 2 | `scratch` | Foundation start | MINIMAL | Org-foundation configurator (guardrails/CI/governance/observability/eval), not a blank slate |
| 3 | `plato` | AI-assisted design | SPEC | Conversational inception → spec-first repo (CLAUDE.md, SPEC.md, TDD skeleton); ships with org foundation harness by default |

All three exit through the same gate: GitHub export with the CI three-gate
workflow pack (`.github/workflows/eval.yml`, `tests.yml`, `compliance.yml`,
written by `export-composer.mjs`). "Three ways in, one gate out" - the
platform's product is the gate, not the generated code (`vDoorLanding` copy).

### 1.4 Observability scope split (`obsScope`, TLP-B9/B10 - R-B10-05)

`S.obsScope = { type, id, label }` drives every obs/metrics/trace call
(`/api/metrics?scope=...&id=...`, `/api/obs-traces`, etc). Two distinct
entry points land in different scopes:

- Admin **Monitoring** nav (`observability` view) → `{type:'fleet', id:'all'}`
  - platform-wide aggregate.
- Domain/platform **`bwobs`** nav (inside BUILD WORKSPACE) → `{type:'domain',
  id:<activeDomain()>}` - that domain's own project detail, not the platform
  aggregate.

A scope chip at the top of the observability view (`#obsscopechip`, index.html
~4111) renders one of two labels depending on `obsScope.type`, so the user
always sees which lens they are in. Other scope transitions: drilling into a
project (`workspace` → `wsobsgo` button) sets `{type:'project', id, label}`;
drilling into an agent trace sets `{type:'agent', id, label}`.

### 1.5 Front-end conventions

- **`esc()`** (index.html ~202): escapes `& < > "` for any server/LLM-derived
  text landing in innerHTML *outside* `md()` - CLI output, eval explanations,
  Langfuse trace fields. All of these are attacker-influenceable.
- **`md()` / `mdInline()`** (index.html ~216–226): escapes HTML first, then
  renders a safe markdown subset (bold/italic/inline code/fences/headings/
  lists). Escape-before-render because chat text is model output. Structural
  classification (heading/bullet/numbered/paragraph) happens *before* inline
  bold/italic parsing, so a leading `* ` is never misread as `<em>`, and
  blank lines between numbered items do not close the list (models emit
  `"1.\n\n2.\n\n3."` and numbering must stay sequential).
- **Door-copy hygiene**: the three-door landing copy is written in product
  language, not demo language - no "mock"/"simulated" wording is used in the
  Create Agent journey text (`DOORS` array), even though the underlying
  export owner default is a mock SSO org (see §2.2). TODO: could not find an
  explicit linter/test enforcing this as a rule; it currently holds by
  inspection of the `DOORS` copy only.

## 2. Backend API Catalog

`console/server.mjs`, single `if (url.pathname === "/api/...")` dispatch chain,
118 route matches (some paths handle both GET and POST - see per-route method).
Grouped by domain below. `can(session, capability)` is the authorization gate
(`capabilities.mjs`); routes with no `can()` call either have no session
requirement (login, catalog reads) or gate via a nested check further down
(annotated where found).

### 2.4 Export (GitHub-first flow)

| Method | Path | Gate | Behavior |
|---|---|---|---|
| POST | /api/export | useBuilderSurfaces | `guardProject`; preset ∈ FULL/MINIMAL/SPEC; owner defaults to a mock org unless real+`confirmReal` |
| GET | /api/export-manifest | (via guardProject) | Preview file list for a preset, no side effects |
| GET | /api/scratch-manifest | useBuilderSurfaces | Foundation-start file list preview |
| POST | /api/scratch-export | useBuilderSurfaces | Foundation-start export; same confirmReal guard |
| POST | /api/plato-export | useBuilderSurfaces | AI-assisted (inception) export; same confirmReal guard |

**confirmReal guard** (`ownerRequiresConfirm`, server.mjs ~2838): looks up the
target owner in `catalog.json` `githubOrgs`; if `org.real === true` and the
request did not pass `confirmReal`, the export is rejected with 400 "real
GitHub org requires explicit confirmation." `defaultMockOwner()` picks the
first `real:false` org as the silent default, so an un-confirmed export never
touches a live GitHub account.

### 2.5 Lifecycle (delivery pipeline state machine)

| Method | Path | Gate | Behavior |
|---|---|---|---|
| GET | /api/lifecycle | useBuilderSurfaces | Reads state for a `repo` |
| POST | /api/lifecycle-advance | useBuilderSurfaces | Advances one stage |

Both validate `repo` against `LIFECYCLE_REPO_RE = /^[A-Za-z0-9._-]+\/[A-Za-z0-9._-]+$/`
(server.mjs ~896) - the two-segment `owner/repo` shape every real export
produces - before touching the store, so client-controlled repo strings are
never echoed back unsanitized (fixes R-B8-02/03, PII/HTML-shaped input).

`lifecycle-advance` (server.mjs 5816):
- Rejects `stage === "exported"` directly (only `exportToGithub` may create
  that stage - R-B8-01a).
- Requires an existing entry (`lifecycleGet`) - no advancing a repo that was
  never exported (R-B8-01b).
- **Member-based ownership** (R-B8-01c / R-015): resolves the owning project
  from the export's history, then checks `(proj.members||[]).some(m =>
  m.principal === session.user)` - any member or lead of that project may
  advance it, not just the original exporter. Falls back to
  exporter-only if there is no project record (ad-hoc export), fail-closed.
- **Order check**: `wantIdx === LIFECYCLE_STAGES.indexOf(entry.stage) + 1`  - 
  exactly one step forward, or 400 "out-of-order stage."

### 2.6 Guardrails

| Method | Path | Gate | Behavior |
|---|---|---|---|
| GET | /api/guardrail-catalog | useBuilderSurfaces | `GUARDRAIL_CATALOG` (PII Detection, Harmful Content, Jailbreaking, Prompt Injection, Topic Restriction) |
| POST | /api/guardrail-config | useBuilderSurfaces | Sanitizes a client-submitted config list via `sanitizeGuardrailConfig` |
| GET/POST | /api/domain-policy | decideAccessRequests + domainScoped | Domain-enforced guardrail tier (spec §4.2) |

**Enforce-lock** (server.mjs ~1436 `lockedGuardrails`/`guardrailListErrors`):
every guardrail-list payload - wizard, legacy create path, or raw curl - must
still include every org-enforced id (`ORG_ENFORCED_GUARDRAILS`: pii-filter,
security-scan-gate) plus that domain's enforced tier from `domain-policies.json`.
Omitting one is a 4xx **reject**, never a silent re-add - the caller learns
the policy exists instead of believing a disable worked.

| Method | Path | Gate | Behavior |
|---|---|---|---|
| GET | /api/memories, /api/memory-extractions, /api/kb-docs, /api/kb-doc | viewDomainOperations | Reads |

**Masking pipeline** (`maskPII`, server.mjs ~2639, "TLP-T32"): demo-grade
pattern-based redaction, always on, explicitly labeled `[simulated]` in code
comments as a stand-in for CloudWatch Logs data-protection policies. Covers
PAN-like digit runs (fragmenting a masked last-10), access keys, and common
bearer-token prefixes - deliberately over-masking free text is the chosen
safe direction. `maskTrace()` wraps input/output through `maskPII` and flags
`masked:true`. Reveal (unmask) is a separate, audited action - every reveal is
logged (`obs-audit` store), never silent.

## 3. Data Stores & Sources of Truth

All stores below live in `console/*.json`, next to `server.mjs`. Most are
gitignored runtime state (self-seeding on first read); check `.gitignore` per
file before assuming version-control history exists for it.

| Store | Role | Source-of-truth note |
|---|---|---|
| `projects.json` | Durable multi-agent workspace records; each has `members`/`leads` | **Real source of membership/attribution.** `lifecycle-advance`'s ownership check and `guardProject`'s domain-visibility check both resolve through this file, not through the agent registry or lifecycle store. |
| `agent-lifecycle.json` | Delivery-pipeline narrative state (exported → in_development → eval_available → deployed → registered) | Gitignored runtime state. This is a **demo-layer pipeline representation**, not the fleet's actual runtime status - a repo can be "registered" here while its live agent state is tracked separately in the fleet. |
| `catalog.json` | `githubOrgs` list with `real: true/false` per org | `real:false` = mock SSO org, silent export default; `real:true` = live GitHub org, requires `confirmReal` on every export call (checked per-request, not cached). |
| `agent-registry.json` | Registry entries synced from the live fleet (`syncAgentRegistry`) | New fleet runtimes auto-register as `DRAFT`; entries whose runtime no longer exists drop out. This is the **registry's own bookkeeping**, distinct from `agent-lifecycle.json`'s pipeline stages. |
| `domain-policies.json` | Domain-enforced guardrail tier | Read by `lockedGuardrails()`; combined with the hardcoded `ORG_ENFORCED_GUARDRAILS` list to compute the enforce-lock floor for every project in that domain. |
| `domain-profiles.json` | Blueprint-derived profiles for project-from-profile flow | Read-only catalog, not written by the API surface documented above. |
| `usage-ledger.json` | Cost/usage line items | **Single computation source for cost.** `/api/costs` and `/api/domain-cost-rollup` both read this ledger; there is no second cost pipeline to disagree with it. |
| `hitl-policies.json`, `alert-policies.json` | Approval-policy and alert-policy config | Governance-gated writes only (`manageApprovalPolicies`, `manageAlertPolicies`). |
| `kb-store.json`, `sim-memories.json` | KB documents / memory extraction fixtures | Domain-plane reads/writes gated by `viewDomainOperations`; attribution to a domain is a separate platform-only action (`attributeMemoryStores`). |
| `eval-fixture.json` | Fixture eval-results, explicitly labeled a stand-in for an S3 read (per B8 acceptance) | Read by `readEvalFixture()`; surfaced honestly in both the API payload and UI copy as a fixture, not a live S3 call. |
| `policy-exemptions.json` | Two-layer 4-eyes exemption records (TTL at layer-2, TLP-B6) | Governance-only writes. |

**Who is the real source, in one line:** agent runnability/status = fleet
runtime state (not tracked in the files above); lifecycle stage = delivery
pipeline demo layer (`agent-lifecycle.json`); project/domain ownership =
`projects.json` members/leads; cost = `usage-ledger.json` alone. These four
axes are intentionally decoupled - a project can be "registered" in the
lifecycle pipeline while its cost ledger and its fleet runtime status are each
tracked independently.
