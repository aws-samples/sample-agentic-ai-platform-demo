Enterprise Agentic AI Platform

A progressive maturity roadmap — from ad-hoc agent sprawl to a self-evolving, platform-as-agent operating model.

An enterprise agentic-AI platform matures across four levels — L1 Ad Hoc Agents → L2 Platform Foundation → L3 Self-Service Scale → L4 Adaptive Platform — and the account topology + platform building blocks grow with it. Each level below shows a detailed multi-account architecture so you can see the platform grow stage by stage.

The platform at a glance

Our point of view in one picture: a governed set of building blocks. Responsible AI and Observability wrap everything; the middle is the capability stack (gateways → hubs → runtime → data & memory); Operations runs underneath. The platform team owns the amber blocks (the Foundation Harness); domain teams differentiate in the green blocks (their Domain Harness).

Level 01 · Ad Hoc Agents

Isolated pilots and experimentation

Teams spin up agents wherever they can — a notebook, a laptop, a lone AWS account. Local prompts and custom code, inconsistent security/access controls, limited tool or knowledge reuse. This is where most enterprises start, and where the deck's four problems originate.

Characteristics: isolated pilots · local prompts & custom code · inconsistent security/access controls · limited tool or knowledge reuse.  🎯 Target action: establish a shared platform mandate and minimum controls.

Symptoms

  • Agent sprawl — duplicated effort, zero reuse
  • Shadow AI — agents outside sanctioned channels
  • Cost blindness — no per-agent token attribution
  • Observability gap — no unified tracing

Account topology

  • No formal design — one account per team, or shared dev sandboxes
  • Secrets in code, manual deploys, no environments
  • Model access direct-to-Bedrock, ungoverned
L1 architecture — every team in its own account, each calling Bedrock directly. No shared plane, no registry, no governance.

Level 02 · Platform Foundation

First shared services — a partial control plane

A platform team stands up the first shared services in a dedicated Platform account: an AI Registry (unified agent · MCP · skill/tool registry), an optional AI Gateway (routing, auth, rate-limit, cost attribution), approved production runtimes, and basic governance / audit logging. Teams can adopt these shared services — but the control plane is not fully built yet: there's no self-service, no prebuilt eval pipeline, no policy-as-code. The platform team still builds and operates most agents by hand.

Characteristics: unified AI Registry (agent/MCP/skill) · optional model gateway & routing · approved production runtimes · basic governance, audit & cost attribution.  🎯 Target action: standardize templates, onboarding, and release gates (→ complete the control plane at L3).

New platform building blocks new

  • AI Registry — one registry for agents, MCP servers, and skills/tools (discovery + versioning)
  • AI Gateway (optional) — routing, auth, rate limiting, cost/token attribution — not yet mandatory
  • Approved runtimes — sanctioned production execution
  • Basic governance — audit logging + centralised observability + identity

Operating pattern & what's still missing

  • Centralised — platform team builds & operates most agents
  • Best for <20 agents / low domain-team capability
  • Not yet: self-service blueprints, prebuilt eval pipeline, policy-as-code, automated gates, multi-env

Level 03 · Self-Service Scale

Approved blueprints, shared control plane, automated quality gates

The platform becomes a product. A Governance / Landing-Zone account provisions a full set of environment accounts (dev → UAT → prod) per domain, on demand, from approved architectural blueprints. Domain teams self-serve on a shared control plane for all agents, ship through automated evaluation and quality gates, and run federated domain-owned runtimes. The governance account vends replicated per-team account sets — and it is exactly what the demo console implements.

Characteristics: approved architectural blueprints · shared control plane for all agents · automated evaluation & quality gates · federated domain-owned runtimes.  🎯 Target action: scale reuse, automate evidence, and improve domain ownership.

New platform building blocks new

  • Approved blueprints — chat / workflow / RAG / MCP Foundation Harness templates
  • Governance account — Service-Catalog-style account vending, IaC, team→account map
  • Automated quality gates — Cedar policy + Guardrails + eval as promotion gate
  • Golden-path CI/CD — commit → test → eval → stage → deploy (agent-as-code)
  • Federated domain-owned runtimes — teams own their data-plane lifecycle

Operating pattern

  • Federated / Hybrid — central control plane + federated application plane
  • Per-domain accounts, per-environment gating (dev/UAT/prod)
  • Data stays in the domain's account; only telemetry flows up
  • Evidence (eval results, traces) automated, not hand-collected
L3 architecture — a Governance account vends full per-domain account sets (dev/UAT/prod); the Platform control plane stays central, execution is federated.

The golden-path lifecycle (agent-as-code)

Within L3, every agent moves through a governed pipeline that loops: build → CI → CD → eval → operate → feed back. Everything that defines an agent (prompt, tools, harness bindings, deploy params) lives in Git — reviewed, tested, evaluated, versioned, reversible. This is AALOE — Agentic AI Lifecycle Operational Excellence: develop → measure → improve, continuously.

Level 04 · Adaptive Platform

AI-assisted, self-optimizing — the north-star

At L4 the platform stops being passive infrastructure and starts to optimize itself. AI automation runs across the lifecycle: AI-assisted onboarding and scaffolding, auto-tuning of evaluation and tools, intelligent operational optimization, and continuous autonomous improvement. The same L3 topology stays; what's new is that AI now drives the toil out of running it. This is a north-star maturity level, not a promise for the first implementation.

Characteristics: AI-assisted onboarding & scaffolding · auto-tuning of evaluation & tools · intelligent operational optimization · continuous autonomous improvement.  🎯 Target action: reduce platform friction and improve continuously.

AI automation layered on L3 new

  • AI-assisted onboarding & scaffolding — describe intent → composed harness + golden-path repo
  • Auto-tuning of eval & tools — the platform proposes prompt/model/tool changes from eval signal
  • Intelligent ops optimization — model routing, cost, and rollout tuned automatically
  • Continuous autonomous improvement — feedback-driven lifecycle updates (self-optimizing flywheel)

Where the automation acts

  • Onboarding: turns a requirement into a composed Foundation + Domain Harness
  • Build: generates the golden-path repo (config + guidance) and opens the PR
  • Pipeline: runs the L3 CI / eval-gate / deploy as guided or automated steps
  • Operate: monitors online eval and proposes prompt/model improvements
L4 architecture — same L3 topology, now with an AI automation layer ("platform as agent") that assists onboarding and continuously optimizes the running platform.

How the account topology grows

The agentic landing zone expands as maturity increases. Durable shared accounts (Platform, Governance) persist; per-domain environment accounts are vended and decommissioned on demand. The right-hand column shows what changes for the agents themselves at each level.

LevelAccountsControl planeHow agents are built & run
L1Ad-hoc, one per team (or none)NoneEach team hand-builds isolated agents; direct model calls, no reuse
L2+ Platform accountPartial — gateway · approved runtimes · registry · basic governance (no blueprints / eval pipeline / policy-as-code yet)Agents run in single-env domain accounts; platform team manually builds & promotes most of them
L3+ Governance account + per-domain dev/UAT/prod setsComplete — blueprints · prebuilt eval pipeline · policy-as-code · automated gates now lit upDomain teams self-serve agents from blueprints; golden-path CI/CD with eval as the promotion gate; federated domain-owned runtimes
L4Same topology + AI automation layerSelf-optimizing on top of L3AI assists onboarding/scaffolding & auto-proposes improvements to running agents; humans approve
Consistent thread across all levels: reproducibility (agent-as-code in Git), auditability (trace → commit → deploy), reusability (blueprints + skill registry), environment parity (dev/UAT/prod from one IaC), separation of concerns (accounts enforce boundaries), and provider-agnosticism (gateway abstracts the model).
